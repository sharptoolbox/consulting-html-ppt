三条硬规则（与主提示词一致）：
① 一张图只允许一处红色 —— 落在“最该被看见”的那一个组件 / 环节；其余一律走深蓝、深灰、灰及其平涂深浅阶，禁渐变 / 阴影 / 3D。
② 同层同底 —— 同一层（区）内的组件统一用同一个底色，层级只靠底色档位与左侧标签条区分，不靠颜色数量。
③ 连线接在边的中点 —— 优先直角走线（elbow）；一张图的连线交叉不超过 2 处，超过就说明这一页该拆了。

00

图元与连线规范

画法总则 / 图元 / UML 记号 / 配色 分栏 1120×700
用在：每一次画架构图之前先读这一张 —— 它是本库的“图元字典”，规定了组件块、分层带、系统边界、数据存储、消息队列、网关的统一画法，以及 9 种关系记号、5 种行为图元。
关键配置：块 = 圆角矩形 rx=4；层 = 色块标签条 + 底板（直角，避免圆角缝隙）；边界 = 虚线框 + 左上角标；存储 = 圆柱；队列 = 左双竖条；网关 = 六边形。连线一律 stroke-width:1.5，接点落在边的中点；实心箭头＝同步，开放箭头＝异步，虚线＋开放箭头＝返回 / 依赖，空心三角＝继承 / 实现，实心菱形＝组合，空心菱形＝聚合。
慎用：不要在同一个组件上叠两种记号；不要在矩形角点接线（斜线一多，整张图立刻显得业余）。
01

分层技术架构图（五层）

总体架构 / 系统分层 / 技术全景 分栏 1120×700
用在：软件方案的“总体技术架构”页 —— 回答“这套系统分成几层、每层有什么”。五层自下而上：用户与接入层 / 业务应用层 / 平台服务层 / 数据资源层 / 基础设施层，底部压一条横向保障体系带。
关键配置：层底板宽 1120、高按内容 80–124；左侧标签条统一 100px；层间间距 13px；层内组件左右留 10–16px、上下留 15–24px。业务 / 平台层用浅蓝底 #F0F6FA + 蓝标签条，接入 / 数据 / 基础层用浅灰底 #F5F5F5 + 深灰标签条。唯一红色落在一个核心组件上（本图为例：订单交易中心）。
慎用：层数超过 6 层就拆成两页；不要画穿层箭头（斜穿整张图的箭头会毁掉分层感，支撑关系靠“层序”本身表达）。
02

分层技术架构图（六层 · 通栏）

总体架构 / 系统分层 / 技术全景 通栏 1880×700
用在：需要在一页里讲全“渠道—应用—能力—数据—技术—基础设施”六段结构的场合，只能放通栏。比 01 粒度更细：每层组件更多、且带右侧“体系保障”竖栏。
关键配置：左侧标签条 120px、右侧体系栏 140px，中间内容区 1592px（组件行按 6 / 4 / 8 / 6 / 7 / 6 分布）；行间距 14px；右侧体系栏用虚线框 + 3 个竖排文字块（标准规范 / 安全保障 / 运维保障）。
慎用：每层组件超过 8 个时不要硬塞 —— 改回 01 的“层内两行”写法；右侧体系栏不得超出 3 项，多于 3 项说明这不是“体系”而是功能清单。
03

应用架构图（域 × 应用）

应用全景 / 业务域切分 / 系统清单 分栏 1120×700
用在：“应用架构 / 系统功能地图”——回答“有哪些应用、分别归哪个业务域、靠什么公共能力支撑”。顶部统一门户 + 中部 4 个业务域（每域 4 个应用）+ 底部两条公共服务。
关键配置：域列宽 268、列间距 16；域标题栏高 54 走纯色（蓝 / 深灰 / 灰三档语义色），列内应用高 66、间距 12；底部两条通栏高 76、间距 16。域标题用 16px 白字，应用名 15.5px。
慎用：业务域 2–5 个为宜（4 个最稳）；每域应用超过 5 个就该拆页或换 05 功能架构图。域 ≠ 部门：按业务能力切分，不要按组织架构切分。
04

数据架构图（六层流水）

数据治理 / 数仓分层 / 数据流向 通栏 1880×700
用在：“数据架构 / 数据流向”——回答“数据从哪来、怎么存、怎么算、给谁用”。六层自上而下：数据应用 / 数据服务 / 数据计算 / 数据存储 / 数据集成 / 数据源，右侧竖栏压“数据治理”。
关键配置：左侧标签条 120px、右侧治理栏 140px；行间距 16px；存储层一律用圆柱（与集成 / 应用层区分开）；计算层写“组件 + 技术选型”两行。治理栏 4 项：数据标准 / 数据质量 / 数据安全 / 元数据管理。
慎用：ODS–DW–数据湖的层名不要混用中英文缩写，要么全写“贴源层 / 数据仓库 / 数据湖”，要么全写 ODS / DW / Data Lake；治理栏是“横向能力”，不要误当成数据流的第七层。
05

功能架构图（模块 × 功能）

功能清单 / 需求范围 / 模块划分 通栏 1880×700
用在：“功能架构 / 需求范围”——回答“这套系统一共要建哪些功能”。四大模块 × 每组 4 项功能（共 32 项）+ 底部公共支撑。
关键配置：模块列宽 455、列间距 20；模块标题栏高 56（纯色）；二级分组标题栏高 38（浅灰底 + 3.5px 模块色短竖线）；功能项高 36、间距 8。底部公共支撑通栏高 56。
慎用：功能项名一律 4–6 字（“客户档案”“合同变更”），写成长句会立刻变成需求文档；每列功能项 ≤ 8，超出说明模块没拆干净。

06

微服务架构图

技术架构 / 服务拆分 / 中间件选型 分栏 1120×700
用在：技术架构细化 —— 回答“服务怎么拆、中间件选什么、治理能力有哪些”。
关键配置：客户端 3 个（311×56）→ 六边形 API 网关（全宽 966×56，蓝底白字）→ 服务注册与配置中心（浅蓝通栏 48）→ 8 个微服务（2×4，231×64，唯一红落在核心服务）→ 中间件层（管道形状 ×4）→ 数据层（圆柱 ×4）→ 底部可观测与治理通栏。右侧 140px 虚框“服务治理”竖栏 4 项。
慎用：微服务 ≤ 8 个（超过就抽象成“业务中台服务群”）；网关必须画成六边形，用矩形会与普通服务混淆；中间件四格不要混写（消息 / 缓存 / 事务 / 调度各占一格）。

集成关系图（总线型）

系统集成 / 接口清单 / 内外部打通 通栏 1880×700
用在：系统集成 / 接口清单 —— 回答“我们和哪些系统打通、用什么方式打通”。
关键配置：总线型布局。中间一条 1698×46 深色“统一集成总线”（左端 190px 蓝色块为集成平台），上排 4 个内部业务系统（359×92）、下排 4 个外部系统（虚线描边区分内外），右端接数据中台。连线用 4 种线型分别对应 REST / MQ / 文件 / 数据库直连，并把协议标注在连线上；底部图例复述一遍。
慎用：一张图最多 4 种集成方式；外部系统一律虚线描边；不要在总线上画“双向箭头对穿”——方向靠上下排布表达。

安全架构图（纵深防御）

等保合规 / 安全体系 / 防护措施 分栏 1120×700
用在：等保合规 / 安全体系 —— 回答“安全分几层、每层做了什么”。
关键配置：顶部“安全策略与管理制度”（浅蓝通栏 52）＋ 5 层纵深防御（每层高 76、左侧 100px 标签条、层内 4 项措施 240×48）＋ 底部“安全运营与应急响应”（56）。层色按“由外到内”由灰转蓝，用来表达纵深。
慎用：层数固定 5 层（物理 / 网络 / 主机 / 应用 / 数据），不要自创层级；每层措施 4 项、名字 ≤ 6 字；唯一红只标一处最关键的防护措施。

架构演进图（三代架构）

现状—过渡—目标 / 技术演进 通栏 1880×700
用在：架构演进 / 技术路线 —— 回答“我们从哪来、到哪去”。
关键配置：顶部时间轴（横线 + 3 节点 + 年份）＋ 三列架构块（586 宽、间距 61、高 430）；每块 = 56 标题栏 ＋ 3 个层次条（554×92）＋ 底部 36px 特征标签。目标态（第三列）标题栏唯一走红。

部署视图（UML Deployment）

网络部署 / 集群规划 / 资源清单 通栏 1880×700
用在：网络部署 / 集群规划 —— 回答“部署在哪、几台、怎么连”。
关键配置：4 个虚线分区（用户侧 300 / DMZ 360 / 应用区 610 / 数据区 400，区间留 70px 用来画跨区连线并标协议）＋ 底部通栏运维区 5 项。节点一律带 «device» / «execution environment» / «artifact» 构造型；集群数量写在节点副标题（“×3”“1 主 2 从”）。连线标注协议（HTTPS / 内网 TCP / JDBC）。
慎用：分区 3–5 个；DMZ 必须与内网分区物理隔开（留出通道画跨区连线）；不要在一个节点里塞 3 个服务 —— 那说明该拆成“K8s 集群 + Pod”两层。

活动图 · 泳道（UML Activity）

业务流程 / 跨角色协作 / 审批链路 通栏 1880×700
用在：业务流程 / 跨角色协作 / 审批链路 —— 带泳道的 UML 活动图最适合 PPT。
关键配置：3–4 条泳道（每条高 210、左侧 140px 角色条、隔行浅底）；圆角矩形 = 动作（240×60）、菱形 = 决策、粗黑条 = 分叉 / 汇合、实心圆 = 开始、同心圆 = 结束。回退线走泳道之间的空白纵向通道，不要斜穿。底部空白区写流程注解。
慎用：泳道 ≤ 4 条；每条泳道内动作 ≤ 4 个；决策分支 ≤ 2 个（是 / 否）；回退线只允许 1 条 —— 两条以上就该拆页。

序列图（UML Sequence）

接口时序 / 调用链路 / 交互设计 分栏 1120×700
用在：接口时序 / 调用链路 —— 回答“一次请求经过谁、按什么顺序”。
关键配置：5 个参与者（190×64、间距 28）＋ 生命线（虚线，止于 y=550）＋ 激活条（12 宽竖条）＋ 消息（同步 = 实线实心箭头，返回 = 虚线开放箭头，标注写在线条上方 9px）。红色只标最关键的一条交互。
慎用：参与者 ≤ 6 个；消息 ≤ 12 条（超过就分“正常流程 / 异常流程”两页）；不要把 if / else 塞进一张序列图 —— 那是两张图。

类关系图（UML Class）

领域模型 / 数据结构 / 实体关系 分栏 1120×700
用在：领域模型 / 数据结构 —— 回答“有哪几个实体、什么关系、基数多少”。
关键配置：三段式类框（类名 40–50 高 ＋ 属性 ＋ 方法，行高 19）；抽象类加 «abstract» 构造型并给浅灰表头。五种关系都示范了一遍：泛化（实线 ＋ 空心三角）、组合（实心菱形）、聚合（空心菱形）、关联（实线）、依赖（虚线 ＋ 开放箭头）。基数标在线的两端、紧贴端点。
慎用：类 ≤ 7 个、每类属性 ≤ 4、方法 ≤ 2（PPT 里这不是代码文档）；菱形必须画在“整体”那一端（画反是最常见的低级错误）；泛化线走空白通道，不要斜穿其他类框。

状态转化图（UML State）

单据状态机 / 流转规则 / 异常分支 分栏 1120×700
用在：单据状态机 / 流转规则 —— 回答“一个单据会经历哪些状态、怎么流转”。
关键配置：主链 5 个状态（156×110、圆角 12）水平排开；分支状态（已取消 / 已退款）挂在主链上方，各接一个终态；转移标注 = 事件（“超时未支付”“退款申请”），写在线条上方。底部压一条“关键流转规则”说明带（高 130，左侧 4.5px 红粗线），把触发条件写清楚。
慎用：状态 ≤ 7 个；转移标注只写“事件”，守卫条件与动作放到底部说明带；初始态 1 个、终态 1–3 个 —— 终态多于 3 个说明状态机没收敛。

第二问 —— 放在页面哪个位置？
分栏页（左文 700 ＋ 间距 60 ＋ 右图 1120）：01 / 03 / 06 / 08 / 12 / 13 / 14 这七张按 1120×700 画；
通栏页（图区 1880×700）：02 / 04 / 05 / 07 / 09 / 10 / 11 这七张按 1880×700 画。
两者高度都是 700，所以字号与线宽不用跟着改，复制出去零折算。

第三问 —— 这一页有什么风险？
① 组件数超了？分层图每层 ≤ 8 个、集成图每侧 ≤ 4 个 —— 超了先拆页，不要缩字号。
② 连线交叉超过 2 处？说明分区没划干净，回 00 重看“直角走线 + 接点落在边的中点”。
③ 一页里出现了两处红？删掉一处 —— 红色只留给“最该被看见”的那一个组件 / 环节。
④ 把框和线全去掉之后只剩几段文字？那这页不是架构图，回主提示词 §2.6 改走文本分类版式。
